# H1 判题终态与学习画像并发试点

## 测量范围和方法

本次在独立 PostgreSQL 数据库 `xmuoj_h1` 使用 60、120、240 名学生的假设班级规模；尚未收到生产班级规模或实际 SLA。建议的本机试点目标为“突发开始至落库 P95 ≤ 1 秒，突发开始至画像就绪 P95 ≤ 30 秒”，不是生产承诺。

测试环境为本机 Python 3.11 + Django 3.2，PostgreSQL 14 容器位于 Colima x86_64（QEMU amd64）虚拟机。Docker 报告 3 vCPU、约 3.82 GiB 内存（4100120576 bytes）。正式性能采样等待镜像构建与 H5 RAG 基准停止后才运行，避免人为并行压测互相污染。网络仅为 macOS 到本机虚拟机的数据库连接。

每名学生先有 20 条历史提交，4 道公开题共享 2 个知识点，每个映射权重为 0.5。历史 fixture 使用真实 `capture_submission` 生成的映射和输入模板批量建立，再经真实 `replay_user` 建立初始评分。同一群体依次参加 60、120、240 人场景，前一轮参与过的学生会保留已有新增提交；JSON 中记录每轮历史条数范围，避免把 20–22 条误写成全部严格 20 条。

突发阶段使用 4 个判题终态线程及 4 个画像线程（与部署每进程 4 个线程的配置对应；并非给 240 人开 240 个连接）。每名学生一条新 AC，同时排入该班每人的完整画像重算：

1. 在与 `JudgeDispatcher._judge` 相同的事务边界内执行真实 `Submission.save()`、post-save outbox capture、`JudgeDispatcher.update_problem_status()`。
2. outbox 提交回调投递到本次进程私有的队列，再由独立线程执行真实 `process_event/replay_user`。不会向共享 Redis/Dramatiq 队列投递消息。
3. 记录排队、事务执行和“突发开始至提交完成”的 P50/P95/P99/max；分别记录提交后画像滞后、突发开始至画像就绪、画像任务执行时间。
4. SQL 执行包装器测量 advisory-lock 和 `FOR UPDATE` 语句耗时，包含数据库执行/往返开销；**不能把这些时间当成纯锁等待**。另以 20ms 间隔查询 `pg_stat_activity.wait_event_type='Lock'`，报告最高等待连接数、锁类型及近似 session wait 总量。采样估计可能漏掉短等待。
5. 校验终态/事件无丢失、所有 revision 已处理、history 条数、学生尝试/通过次数、旧题目计数、题目知识评分计数，以及脱离并发队列后再次完整重算所得评分完全相同。

此实验覆盖数据库事务、锁、画像重放和受限线程队列；**不包含**浏览器/HTTP、真实 JudgeServer 执行、代码沙箱、外部模型、真实 Dramatiq/Redis 传输或生产机器。后者必须在 H7 与真实部署验收中单独验证。

## 复现命令

仅允许脚本操作精确命名的可丢弃 PostgreSQL `xmuoj_h1`；`--reset` 会清空这一隔离库的数据，不接受其他库名。以下用当前修复后的代码复跑，输出到新文件，保留本次基线与 after 原始证据。

```sh
POSTGRES_HOST=127.0.0.1 POSTGRES_PORT=15432 POSTGRES_DB=xmuoj_h1 \
POSTGRES_USER=onlinejudge POSTGRES_PASSWORD=onlinejudge REDIS_PORT=16379 \
.venv/bin/python backend/manage.py migrate --noinput

POSTGRES_HOST=127.0.0.1 POSTGRES_PORT=15432 POSTGRES_DB=xmuoj_h1 \
POSTGRES_USER=onlinejudge POSTGRES_PASSWORD=onlinejudge REDIS_PORT=16379 \
.venv/bin/python tools/benchmark_learning.py --reset \
  --output docs/reviews/backend-h1-h7-evidence-2026-10-07/h1/after-rerun.json
```

## 结果

60 人基线已失败，原始数据为 `baseline.json` 与 `baseline-log.txt`。60 个终态都提交，但只有 58 个新学习事件；PostgreSQL 报告 3 次 `55P03`，其中 2 次采集异常被 signal 吞掉、1 次画像任务失败。落库含排队 P95/P99 为 61.868/63.169 秒，画像提交后滞后 P95 为 59.767 秒，图锁语句 P95 为 4.622 秒、最高 7 个连接等待。总运行 95.572 秒，工作线程执行 6461 条 SQL。

`learning_rating:global` 锁语句 P95 只有 17.115ms，是因为排队已经发生在更早的知识图全局锁上；这不能作为可删除评级锁的证据。本轮保持两者的边界和知识快照语义。

发现 60 人已存在事件丢失后，停止正在运行的 120 人基线；120/240 人基线均记为未完成，不推算数据。基线 `legacy_user_counts=false` 另包含夹具缺陷：初始 20 条历史没有同步填充旧用户 JSON，因此不能把这一项当作业务并发缺陷。after 已按同一历史填充旧 JSON；缺事件和锁超时的证据不依赖此夹具问题。

## 已实施修复与异常边界

- `Submission.save()` 将模型写入及 post-save 学习采集放进同一个事务，覆盖没有外层 `atomic()` 的正常保存。采集失败不再吞掉，而是抛出不含私有详情的 `LearningCaptureError`；真实判题终态及旧计数一起回滚。
- 只有捕获中的 `OperationalError` 或标明 `retryable` 的契约冲突会使判题任务进入新增重试。Dramatiq 1.16 的 `retry_when` 会绕过 `max_retries`，所以条件函数本身也明确限制最多 3 次重试（初始执行加 3 次）。其他程序错误不会因此反复重试；其他非捕获位置的数据库异常不在这一新增策略范围内。
- 自动重试耗尽或发生不可重试错误后，提交可能保留 `JUDGING`，不表示已成功判完。运维修复根因后使用 `python manage.py recover_judge <submission_id>` 明确重投；命令仅接受 JUDGING 和有效未禁用的提交所有者。消息仍经过现有 `submission_worker_lock`，正在执行或已经完成的重复投递不会重复判题。没有无限自动恢复承诺。
- 已存在的旧版本缺事件、`QuerySet.update`/`bulk_*` 等绕过模型信号的写入，仍由 `recover_learning --backfill --sync` 修复；不能把普通 `save()` 的原子保证扩大到这些绕过路径。
- 图锁和评级锁均保留。画像状态改为批量创建/更新，题目知识统计改为按所有受影响 `(problem, knowledge)` 一次分组聚合再批量更新。仍从完整持久历史计算权威计数，重判移除的旧组合也会归零，其他学生贡献保持不变。
- 没有既有学习事件的新非学习状态（如初始 PENDING）提前返回，不再无意义地等待全局学习锁；已有事件进入 JUDGING/系统错误时仍采集撤回修订。

## 回归验证与 after 方法

`learning + judge + submission` 功能回归一次运行 56 项通过（147.271s；当时新测试类继承了旧判题用例，随后已去掉重复定义）；另 2 项针对性回归通过（7.966s），验证旧事件修订回滚后不投递，以及新 PENDING 不获取图锁。覆盖直接 autocommit 保存失败、真实 JudgeDispatcher 首次捕获失败后重投、恰好一次事件与旧计数、重试边界、显式恢复入口，以及跨用户/多个知识点统计保留与重判归零。最终全库回归由主任务统一记录。

修复后工具的私有队列执行同一有界判题重试条件；为避免使用共享真实 broker，本地确定性退避为 1/2/4 秒，并在 JSON `retries` 记录，延迟计入任务完成时间。学习任务同样最多重试 3 次。该退避占用本地测试线程，和真实 Dramatiq 释放线程、经 broker 调度的延迟并不等价；本轮各档确实发生重试，因此不能把这些延迟当成真实 broker 的完整链路结果。

三档 after 均已完成，进程退出码为 0。`after.json` 为完整指标，`after-log.txt` 为原始运行日志；测量结束核对 6 个源码文件的 SHA-256 均与采样记录一致。日志中的 `learning_capture_failed` 是本轮确实发生的捕获锁超时，不能隐藏为“没有错误发生”；表中“最终错误”表示重试后仍未完成的任务。

60 人工作线程 SQL 从 6461 条降为 4153 条（约减少 35.7%），队列完成时间由 95.572 秒降为 84.331 秒，但落库含排队 P95 从 61.868 秒到 60.331 秒，仅小幅改善。由于 after 同时启用可靠性重试并修正旧计数 fixture，这不是仅改变一个变量的微基准，不把差额全部归因于某一条 SQL 优化。可靠性的实质变化是：原先锁超时会提交终态却永久漏事件，现在同类捕获失败回滚终态并在本轮有限重试内恢复全部事件。

## 容量结论与上线前剩余工作

**本次容量试点未通过。** 60/120/240 三档均未达到建议的“落库含排队 P95 ≤ 1 秒、突发至画像 P95 ≤ 30 秒”。这些数字来自 macOS + 本机 QEMU amd64、约 4 GiB 内存的隔离数据库实验，既不是生产 SLA，也不能据此宣称生产吞吐量。

实测等待集中于知识图全局 advisory lock（各档最高 7 个连接等待、图锁语句 P95 约 4.7–5.0 秒）。完整画像重算和新终态采集竞争同一全局图锁，串行工作量与跨虚拟机 SQL 往返叠加，队列随人数增长。评级全局锁的低语句耗时只是已在上游锁串行，不能据此直接将 `global` 改为 `user_id`；知识映射快照与跨用户题目统计仍依赖现有一致性边界。

上线前应在原生目标机器、实际班级规模与确认的 SLA 下复验相同突发场景，并补上真实 HTTP、Dramatiq 与 JudgeServer 完整链路。如果目标机器仍不达标，再单独设计锁粒度及跨用户统计的一致性方案。本轮完成可靠性修复和保留锁边界的批量 SQL 最小优化，不为内部建议阈值继续扩大架构。
