# JudgeServer 心跳并发注册与唯一约束迁移

## 故障与修复

真实 H7 冷启动中，同一 hostname 的两个首次心跳均查询不到记录，随后各自创建一行。由于原表没有唯一约束，后续心跳的 `.get(hostname=...)` 抛出 `MultipleObjectsReturned`，服务不再刷新可用状态，判题提交持续等待。现场原始异常保存在 `docs/reviews/backend-h1-h7-evidence-2026-10-07/h6-h7/first-failure-heartbeat-trace.txt`。

`JudgeServer.hostname` 现在有数据库唯一约束，心跳使用 Django 3.2 的 `update_or_create`。唯一冲突时重读已有记录；更新已有记录时持行锁。心跳只写版本、CPU 核数/使用率、内存使用率、IP、服务 URL 和心跳时间，保留主键、创建时间、`task_number` 和管理员 `is_disabled`。新旧记录的 IP 都使用现有请求中间件解析的 `request.ip`；修正了原先更新遗漏 `cpu_usage` 的问题。

`ChooseJudgeServer` 的占用与释放机制保持原样：进入时为选中的记录加一，退出时按最初保存的主键减一。数据库行锁使心跳和占用计数更新串行。不能把活跃重复记录的计数相加后删除旧主键，否则正在执行的任务会向已删除记录释放，存活记录的槽位永远无法回收。

## 已存在重复行的迁移规则

新增 `conf.0005_judgeserver_hostname_unique` 在一个事务中取得 `judge_server` 表锁，防止旧版本心跳和新任务分配穿过检查，然后执行：

1. 先检查所有重复组的每一条 `task_number`，必须逐条等于 0。任意正数、负数或正负相加为 0 的组均拒绝迁移；全部数据和迁移状态回滚。异常只说明维护要求，不输出令牌或服务凭据。
2. 对全零重复组，保留最小主键和其创建时间，将最新 `last_heartbeat` 的所有遥测字段复制到保留行；时间相同时用主键作为确定性次序。任何一行被禁用，则保留行仍禁用。
3. 删除这些没有在途槽位的重复配置行，再添加 hostname 唯一约束。其他 hostname 的记录保持不变。

项目模型和历史迁移中没有指向 `JudgeServer` 的外键；自行添加的数据库依赖应由维护人员另行核对。反向迁移可以移除唯一约束，但不能重建已经合并的重复配置元数据。

## 升级维护边界

出现非零重复组时，迁移会直接失败，不持锁等待计数变零，以免阻止 worker 的退出释放。应先阻止新任务派发和心跳注册，让已有 worker 完成并释放计数，再重跑迁移。若 worker 已异常退出而计数残留，需在确认相关任务已停止后由维护人员核对修复；本迁移不会自动归零或假定任务已结束。

现有 entrypoint 会在迁移之后重置全部 `task_number`，因此它不能绕过本迁移的非零拒绝检查。该旧启动行为仍要求完整冷启动维护窗口，不能据此宣称多个 backend 的滚动部署会保留所有在途计数。本次没有修改这一启动策略。

专项回归在隔离数据库 `test_xmuoj_heartbeat` 运行。随后主任务用最终镜像启动 `xmuoj_h7`，由启动迁移自动处理原有重复记录；没有手工删行绕过问题。最终查询为1条主机记录、无重复hostname、任务占用归零。

## 验证

- 修复前，PostgreSQL 两连接 Barrier 回归稳定产生两条同名记录；数据库唯一性检查和 CPU 遥测更新检查也失败。证据 `h6-h7/heartbeat-before.txt`。
- 修复后，完整 conf 回归 23 项通过（27.380 秒），包含首次并发注册、后续心跳、数据库唯一约束、占用期间心跳保留主键/计数/禁用标记及退出归零、全零重复组迁移和非零迁移回滚。为避免影响真实联调，测试仅替换了心跳后的待判队列唤醒，不访问共享待判队列；心跳、数据库和迁移均真实执行。证据 `h6-h7/heartbeat-after.txt`。
- Python flake8 通过；`makemigrations conf --check --dry-run` 报告 `No changes detected in app 'conf'`。
- 额外加强迁移回归 2 项通过（28.652 秒）：分别验证 `(1, 0)`、`(-1, 0)` 和 `(1, -1)` 全部拒绝且数据逐字段保持不变，最新遥测全部字段及保留主键/创建时间一致。结果见 `h6-h7/heartbeat-migration-boundaries.txt`。
