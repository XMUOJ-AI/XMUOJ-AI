# 2026 第二批大创项目计划书

## 公共前置阶段：多平台题库采集与标准化（两个项目共享）

### 定位

两个项目都依赖丰富的题库数据：演武场需要足够多的题目来做可视化覆盖，领航员需要跨平台题目来构建知识图谱和推荐系统。目前 XMUOJ 的题库以自主出题为主，数量和质量都有提升空间。从 **洛谷、Codeforces、LeetCode（力扣）** 等主流平台系统性地采集优质题目，经过去重、标准化、知识点标注后，统一导入 XMUOJ。

### 采集策略

| 平台 | 采集方式 | 预计采集量 | 难点 |
|------|----------|------------|------|
| **洛谷 (luogu.com.cn)** | 公开API + 网页爬取 | ≥1000题（P1000-P4000区间的高质量题目） | 反爬策略较强；标签体系需映射 |
| **Codeforces** | 官方开放API（`codeforces.com/api`） | ≥500题（Rating 800-2400，覆盖全难度） | 英文题目需翻译或保留原文+中文摘要 |
| **LeetCode 力扣** | 网页爬取（中国站 leetcode.cn） | ≥300题（Hot 100 + 剑指Offer + 经典题） | 需要登录态；题目描述为富文本HTML |

### 工作内容

#### 1. 爬虫开发（2周，1人）

- **洛谷爬虫**：使用 Python `requests` + `BeautifulSoup`，解析题目列表页和详情页。尊重 robots.txt，设置请求间隔（≥3秒）
- **Codeforces 爬虫**：使用官方 API `problemset.problems` 接口，无需爬页面，数据格式规范
- **LeetCode 爬虫**：使用 `leetcodecn.com/graphql` 接口，需要模拟登录Cookie。优先采集有官方题解的题目
- 所有爬虫输出统一的中间JSON格式（见下方）
- 断点续传 + 增量更新支持

#### 2. 数据标准化（2周，1人）

**统一中间格式**（一道题的标准化表示）：
```json
{
  "source_platform": "luogu",
  "source_id": "P1001",
  "source_url": "https://www.luogu.com.cn/problem/P1001",
  "title": "A+B Problem",
  "description_html": "<p>输入两个整数a,b，输出它们的和。</p>",
  "input_description_html": "两个整数，空格分隔",
  "output_description_html": "一个整数",
  "difficulty": 1,
  "difficulty_source": "luogu_difficulty",
  "tags": ["入门", "模拟"],
  "samples": [{"input": "1 2", "output": "3"}],
  "time_limit_ms": 1000,
  "memory_limit_mb": 128,
  "has_solution": true,
  "solution_hint": "直接使用加法运算符"
}
```

**标签映射表**：将三个平台的标签体系统一映射到项目二的 80+ 知识点分类体系。

| 洛谷标签 | Codeforces Tag | LeetCode标签 | 统一知识点 |
|----------|---------------|-------------|-----------|
| 动态规划,dp | dp | 动态规划 | DP |
| 深度优先搜索,dfs | dfs and similar | 深度优先搜索 | DFS |
| 最短路 | shortest paths | — | 图论·最短路径 |
| 线段树 | data structures | 线段树 | 数据结构·线段树 |
| 贪心 | greedy | 贪心 | 贪心算法 |
| ... | ... | ... | ... |

#### 3. 去重与质量过滤（1周，1人）

- **跨平台去重**：基于题目标题的文本相似度（编辑距离 + TF-IDF），识别同一道题在不同平台上的版本
- **质量过滤规则**：
  - 排除纯模板题（如"输出Hello World"）
  - 优先保留有官方题解的题目
  - Codeforces Rating ≤800 的过于简单的题暂时不导（除非经典）
  - 优先保留中文题目（洛谷、LeetCode中国站）
- **人工抽检**：随机抽取 5% 的采集结果，人工检查题目质量

#### 4. 导入 XMUOJ（1周，1人）

- 基于 XMUOJ 现有的 **FPS（Free Problem Set）格式** 导入机制
- 用 Django Management Command 批量导入：`python manage.py import_problems --source ./collected/`
- 导入时自动关联统一知识点标签
- 保留来源平台信息（`source` 字段标注平台名 + 原始链接）

### 三、分阶段实施计划

#### 第一阶段：Trace 引擎（3个月，2人）

**目标**：让C++算法代码在执行时输出结构化中间状态。

**技术方案**：
- 设计一套轻量的 Trace 宏库（`trace.hpp`），学生只需在关键位置插入 `TRACE_STEP(state)` 即可
- 不用修改 JudgeServer 的判题流程。学生在本地或 Web IDE 中运行代码时，产生 JSON Trace 文件
- Trace 格式示例（DFS 搜索树）：
```json
{
  "algorithm": "dfs",
  "steps": [
    {"type": "enter", "node": 0, "depth": 0, "state": "visiting root"},
    {"type": "recurse", "from": 0, "to": 1, "edge": "left"},
    {"type": "backtrack", "from": 1, "to": 0},
    {"type": "exit", "node": 0, "result": 42}
  ]
}
```
- 覆盖的算法类型：枚举（全排列）、递归（汉诺塔、斐波那契）、分治（归并排序、快速排序）、DFS（迷宫、N皇后）、BFS（最短路）、动态规划（背包、LCS）

**交付物**：
- `trace.hpp` 头文件库，覆盖率 ≥6 种核心算法
- 每种算法的参考实现 + Trace 示例
- Trace 格式文档

#### 第二阶段：可视化前端（3个月，1人）

**目标**：在 XMUOJ 前端的题目详情页嵌入可视化面板。

**技术方案**：
- 基于 **D3.js**（4.x 或 5.x，兼容 Vue 2）构建以下可视化组件：
  - `SearchTreeViewer`：树形布局，动画展示 DFS/BFS 节点展开、回溯
  - `DPTableAnimator`：表格网格，逐步高亮填充单元格（值 + 方向箭头）
  - `RecursionTreeViewer`：调用栈树，展示参数传递和返回值
  - `SortingBars`：柱状图动画，展示归并/快排的分割与合并
  - `GraphExplorer`：图遍历的高亮边 + 队列/栈状态
- 所有组件支持：
  - **播放控制**：播放/暂停/步进/后退/调速
  - **状态高亮**：当前执行行对应代码高亮
  - **自适应布局**：树节点数≤100 时自动排版
- 嵌入位置：XMUOJ 问题详情页新增 Tab：`[题目描述] [提交代码] [算法可视化] [AI导学]`

**交付物**：
- 5 个可视化组件（含单元测试）
- 与 XMUOJ 前端集成的路由和页面

#### 第三阶段：AI 导学 Agent（4个月，3人协动）

**目标**：实现能够根据可视化 Trace 给出分步引导的 AI Agent。

**技术方案**：
- **Agent 框架**：选择 **LangChain**（生态更成熟，文档更丰富，适合本科生上手）或 **tRPC-Agent**（腾讯内部框架，如果团队有相关资源）
- **LLM 接入**：通过 DeepSeek API（低成本，中文友好），配置 prompt 模板
- **核心 Tools**（Agent 可调用的工具函数）：
  1. `get_problem_detail(problem_id)` → 题目描述、样例
  2. `get_trace(visualization_id)` → 当前可视化的 Trace 数据
  3. `get_current_step()` → 当前播放到第几步
  4. `recommend_similar_problems(topic)` → 推荐相关练习题（对接项目二的API）
  5. `get_student_submission_history(user_id)` → 历史提交记录
- **导学策略**（按算法类型定制）：
  - **搜索**：引导学生说出"为什么在这一步选择这个分支而不是另一个"
  - **DP**：引导学生填写 DP 表的递推关系，Agent 检查对错
  - **分治**：引导学生正确识别 base case 和递归拆分
- **后端 API**：新增 Django app `agent_tutor/`
  - `POST /api/agent/chat` — 发送消息，返回 AI 回复 + 推荐动作
  - `GET /api/agent/sessions` — 会话管理
  - `GET /api/agent/hint/{problem_id}` — 请求提示（渐进式：方向提示 → 方法提示 → 伪代码 → 代码片段）

**交付物**：
- LangChain Agent 服务（含 5 个 Tool）
- 覆盖 ≥3 种算法类型的导学 prompt 模板
- 前端 AI 对话面板组件

#### 第四阶段：集成与测试（2个月，全体）

**目标**：所有组件集成到 XMUOJ，在真实教学场景中验证。

**工作内容**：
- 将可视化组件和 AI 导学面板集成到 XMUOJ 前端（不破坏现有功能）
- 选取 程序设计实践 课程的一个班级作为试点
- 收集使用数据：学生平均在可视化上停留的时间、使用 AI 导学后的 AC 率变化
- 根据反馈迭代

**交付物**：
- 集成后的 XMUOJ 测试环境
- 用户测试报告（≥20名学生）
- 使用文档（学生版 + 教师版）

### 三、分阶段实施计划

#### 第一阶段：知识图谱构建（2个月，2人）

**目标**：构建 XMUOJ 题库的算法知识点依赖图谱。

**技术方案**：
- **知识点定义**：参考《算法导论》和程序设计实践课程大纲，将算法知识分解为约 **80-120 个知识点节点**
  - 粒度示例：`递归` → `递归终止条件`、`递归树`、`尾递归`、`记忆化递归`
  - 粒度示例：`DP` → `DP状态定义`、`DP转移方程`、`背包DP` → `01背包`、`完全背包`
- **依赖关系**：定义 `prerequisite` 边（A → B 表示必须先掌握 A 才能学 B）
  - 示例：`递归终止条件` → `记忆化递归` → `DP状态定义` → `01背包`
- **题目-知识点映射**：
  - 为 XMUOJ 上≥200 道算法题 + 采集自洛谷/CF/力扣的≥500 道高频题标注知识点标签
  - 利用"题库采集"阶段产出的标签映射表，自动打标 + 人工校验
- **数据模型**（Django models）：
  ```python
  class KnowledgeNode:
      name, description, category, difficulty_level
      prerequisites: ManyToMany[KnowledgeNode]  # 前置依赖
      
  class ProblemKnowledgeMapping:
      problem_id, knowledge_node, relevance_score  # 题目与知识点关联强度
      
  class StudentSkillProfile:
      user, knowledge_node, mastery_score, last_updated
  ```
- **图存储**：使用 **NetworkX**（Python 图算法库）+ 邻接表存储在 PostgreSQL。如果需要图数据库，可以用 **Neo4j Community Edition** 但 NetworkX 对 ≤200 节点的图已足够高效

**交付物**：
- ≥80 个知识点节点 + 依赖边
- ≥200 道题目的知识点映射
- Django Admin 知识点管理界面
- 前端知识图谱 D3.js 力导向图组件

#### 第二阶段：学生能力诊断（3个月，2人）

**目标**：根据学生的 XMUOJ 提交记录，自动诊断薄弱知识点。

**技术方案**：
- **掌握度算法**：
  - 不是简单地看 AC/WR。引入 **Elo Rating 变体 + 时间衰减**：
    ```
    mastery(topic) = Σ( weight(status, time_ago) × difficulty )
    ```
  - 对每个知识点，综合以下信号：
    - 首次提交即 AC（高掌握）
    - 多次 WA 后 AC（中等，说明有困难但最终攻克）
    - 提交了但从未 AC（薄弱）
    - 从未提交过该知识点的题（未知）
    - 最近一次提交距今时间（时间衰减：越久远的AC越不能证明当前掌握）
- **薄弱点推理**：
  - 如果学生 A 应该在 `01背包` 上有 ≥70% 的掌握度（前置知识点都已掌握），但实际 ≤30% → 标记为薄弱
  - 利用前置依赖链推断"根因薄弱点"：如果 `DP状态定义` 薄弱，则 `01背包` 的失败可能根因不在背包本身
- **API设计**：
  - `GET /api/navigator/profile/{user_id}` → 学生能力雷达图数据
  - `GET /api/navigator/weakness/{user_id}` → 薄弱知识点列表（排序）
  - `GET /api/navigator/progress/{user_id}` → 学习进度时间线

**交付物**：
- 掌握度算法实现（含单元测试）
- 学生能力雷达图前端组件（ECharts Radar）
- 薄弱点诊断 API

#### 第三阶段：学习路径推荐 + RAG 答疑（4个月，2人）

**目标**：基于诊断结果推荐个性化学习路径，并提供 AI 答疑。

**技术方案 — 路径推荐部分**：
- **路径生成算法**：
  1. 从知识图谱中提取未掌握节点的拓扑排序
  2. 使用 BFS/拓扑排序，找出"当前可学"的知识点（所有前置已掌握）
  3. 对每个"可学"知识点，推荐 3-5 道难度递增的题目
  4. 生成学习路径：`[知识点A: 题目1→2→3] → [知识点B: 题目4→5] → ...`
- **推荐策略**：
  - 基础巩固模式：先补最薄弱的
  - 竞赛冲刺模式：优先补充对竞赛排名影响最大的高频考点
  - 新课同步模式：跟随课程进度，推荐配套练习
- **API**：
  - `GET /api/navigator/path/{user_id}?mode=remedial|contest|course` → 学习路径

**技术方案 — RAG 答疑部分**：
- **知识库构建**：
  - 数据来源：XMUOJ 题解区、**洛谷/CF/力扣的公开题解**（已采集）、算法教材摘要、优秀学生提交代码+注释、教师讲义。跨平台题解大大丰富了 RAG 的知识覆盖
  - 文档切分：按"题目/知识点"为 chunk 单位，每 chunk 500-1000 字
  - Embedding 模型：使用本地部署的 **BGE-small-zh**（中文优化、轻量）或 API 调用的 text-embedding-3-small
  - Vector Store：**ChromaDB**（轻量，Python 原生，适合嵌入到 Django 项目中）
- **RAG Pipeline**：
  ```
  用户提问 → 查询改写(Query Rewriting) → 向量检索(Top-5) 
  → 关键词检索(Top-5) → 融合排序(RRF) → LLM生成回答
  ```
- **安全边界**：
  - Agent **不做**：直接生成完整AC代码
  - Agent **只做**：解释知识点、分析错误原因、给出思路引导、推荐相关题目
  - 实现方式：在 System Prompt 中明确约束 + 后处理过滤
- **前端UI**：
  - 嵌入在题目详情页的新 Tab
  - 支持对话式交互
  - 每条回复附带引用来源（哪个文档/题解的哪一段）
- **API**：
  - `POST /api/rag/ask` → 提问，返回带引用的回答
  - `GET /api/rag/similar_problems/{problem_id}` → 相似题目推荐

**交付物**：
- RAG 知识库（≥500篇文档chunk）
- ChromaDB 向量存储 + 检索 API
- 学习路径推荐 API + 前端路径面板
- AI 答疑对话前端组件
- 安全边界验证测试

## 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| DeepSeek API 不稳定/涨价 | AI 功能中断 | 预留切换到其他 LLM（如 Qwen）的适配层 |
| 本科生团队 LangChain 学习曲线陡 | 进度延迟 | 第一阶段提供封装好的 Agent 脚手架代码 |
| XMUOJ 前端 Vue 2 老旧 | 可视化组件兼容性 | 可视化组件独立打包，通过 iframe/Web Component 嵌入 |
| Token 消耗超预算 | 经费不足 | 本地部署小型 LLM（如 Qwen2.5-7B）作为降级方案 |
| 两个项目团队信息不同步 | 重复开发 | 共享知识点标签体系、API 文档、每周联合进度会 |
